需求规则 · FR-019

1 业务目标

站内用户自己申请推广别名，并在申请记录里看审核进度。没有记录时是缺省页。

2 页面与入口

  • 申请记录只展示卡片：别名标题、申请时间、审核状态、审核时间。状态为申请中、已通过、已驳回。申请中没有审核时间，显示「—」。
  • 没有申请时进入缺省页，说明还没有申请记录。
  • 右上角「申请别名」打开弹窗。自己输入，去掉空格后的预览，提交后关闭弹窗并出现在列表里。

3 交互规则

  • 提交前去掉空格，再拿去掉后的字去占位和匹配。
  • 提交成功后前端状态为申请中，后台记为审核中。通过后才生效。
  • 一个用户可以同时有多串有效别名，都能拿去让别人搜。

4 边界规则

  • 去掉空格后为空，不能提交。
  • 已被有效别名或审核中申请占住的字符串，不能再提交。
  • 驳回或失效后，这串字释放，之后可以再发给别人。
  • 用户不能自己把别名设为失效。

5 业务流程

见页内「业务流程」。

1 业务目标

运营审核别名、代用户创建别名，并按设备和别名查看游客记录。

2 数据表与字段

  • 别名管理：申请 ID、用户、别名、状态（审核中 / 已通过 / 已驳回 / 已失效）、来源（用户 / 后台创建）、提交时间、处理时间、绑定用户数。点开人数看绑定用户：用户 ID、用户昵称、绑定类型（新用户 / 静默45天用户）、绑定时间。
  • 游客记录：游客 UUID、版本信息、来源（小程序、小米、OPPO 等设备渠道）、首次安装时间、最近启动时间、设备系统（安卓、iOS）、系统版本、设备型号、设备 ID、搜索别名、所属用户（用户 ID 与昵称）、绑定时间、失效时间、状态（未过期 / 已到期 / 运营失效）、注册正式用户（用户 ID 与昵称，未注册为空）。

3 列表与筛选

  • 别名管理：按用户、别名、状态、来源筛选。来源只有用户、后台创建。审核中可通过或驳回，已通过可失效。点绑定用户数打开绑定用户列表。行内进详情。
  • 游客记录：按设备 ID、别名、状态筛选。行内进详情。
  • 创建别名是弹窗：选用户、填别名。创建即已通过。

4 边界规则

  • 后台创建不审核，但仍去掉空格。空的、已被占住的不能创建。
  • 只有运营可以把已通过的别名设为失效。已进账号的绑定仍留在原所属用户。该别名下未过期的游客记录同时变为运营失效，原失效时间视为已到期。
  • 一台设备同时只有一条未过期记录。已有未过期记录时，再搜别名不新开。
  • 运营失效或自然到期之后，要再搜到一串仍有效的别名，才新开游客记录。搜已失效的字不新开。
  • 注册时若同时有未过期的游客绑定和邀请码，账号上级取邀请码的人，设备上的绑定不清，等到它自己的失效时间。
