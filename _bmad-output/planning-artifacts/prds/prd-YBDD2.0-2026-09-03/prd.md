# PRD: AI工作台

## 0. Document Purpose

本 PRD 给产品、UX、架构与后续 Epic 拆分使用。词汇以 §3 Glossary 为准；功能按组展开，FR 全局编号；未与运营当场拍板的口径标 `[ASSUMPTION]`，并在 §10 汇总。YBDD2.0 已有迭代需求后台 UX（`_bmad-output/planning-artifacts/ux-designs/ux-YBDD2.0-2026-08-23/`），那些页面是业务模块 Demo，**不是**本工作台的界面稿。本 PRD 只定义 AI工作台第一刀：两类可验收查询，以及「对话在左、结构化结果在右」的工作面。

## 1. Vision

右豹管理后台业务菜单多、链路长。运营要回答一个具体问题（今天谁在某个品类刷题词、两个用户是不是一条线上的上下级），往往要跨多个列表、筛选项和详情页拼结果。错一次就要重走一遍。

AI工作台把这件事收成一次提问：运营用自然语言说出要查的东西，系统按已批准的查询意图去扫库，把**可核对的表**铺在结果区。对话区只负责提问、澄清和简述；数字与置信来自库，不来自模型口算。

第一刀不追求「什么都能问」。先把已批准的盘点问法做对：题词排名、上下级、自然裂变、邀请、新增团长、项目收益、项目订单、分红。数字来自库，不来自模型口算。

## 2. Target User

### 2.1 Jobs To Be Done

- **功能**：在不切换菜单的前提下，用一句话拿到可抄、可对的表（用户ID、项目、题词量，或两人关系与默认上级）。
- **情境**：客服/运营正在处理用户问题或盘点当日表现，时间紧，记不清该进哪个菜单。
- **情绪**：少踩空、少怀疑「这个数是不是 AI 编的」；结果区字段必须能对回业务库。
- **社交**：把表贴进群或工单时，对方能看懂列名，不必再解释走了哪条后台路径。

### 2.2 Non-Users (v1)

- 终端用户（C 端）。
- 需要 AI **代操作**（改积分、调账、改绑、发礼品）的角色——第一刀只读。
- 数据分析师做开放式探索、自定义漏斗或导出数仓——不是本工作台 v1 用户。
- 未登录或无后台权限的人。

### 2.3 Key User Journeys

内部工具、单一操作角色，旅程从轻。具名场景只保留两条，对应两个种子 Case。

- **UJ-1. 林安盘今日小说类各项目题词榜。**
  - **Persona + context：** 林安，业务运营，群里被问「今天小说谁题词猛」。
  - **Entry state：** 已登录管理后台，从侧栏进入 AI工作台。
  - **Path：** 在对话区输入「今天所有小说类业务提词最多的前三名用户」→ 系统按排名查询执行 → 结果区按小说类项目分组出表。
  - **Climax：** 每个项目看到用户ID、项目名称、题词量；零题词项目仍在，题词量显示「暂无数据」；并列第 3 全部留下。
  - **Resolution：** 林安复制用户ID 回群，不离开工作台。
  - **Edge case：** 意图缺时间或品类时，对话区先补问，结果区不先出一张错表。

- **UJ-2. 陈柯核两个用户是不是一条线。**
  - **Persona + context：** 陈柯，处理用户纠纷的运营，手里有用户ID1、用户ID2。
  - **Entry state：** 已登录，停留在 AI工作台。
  - **Path：** 输入「查用户ID1和用户ID2的上下级」→ 系统按关系查询执行。
  - **Climax：** 有关系则出直属/间属、方向、双方团长等级与用户昵称；构不成上下级则分别给出各自的默认上级。
  - **Resolution：** 陈柯能向对方说明「谁是谁的上级」或「这两人不是一条线，各自上级是谁」。
  - **Edge case：** 缺一个用户ID 或 ID 在库中不存在时，对话区说明缺什么，结果区不假装有关系。

## 3. Glossary

- **AI工作台** — 管理后台内的查询工作面。左侧为对话区，右侧为结果区。v1 只支持只读查询。
- **运营** — 已登录且具备对应数据权限的后台使用者。本 PRD 的唯一第一角色。
- **对话区** — 左侧：提问、澄清、简短结论。不承载完整结果表。
- **结果区** — 右侧：按查询意图渲染的结构化表（及空态文案）。数字与关系以库为准。
- **查询意图** — 已批准问法，分三类：项目业务数据、用户数据、用户关系。
- **赛道** — 项目所属业务赛道，如小说、短剧。题词榜与分红按赛道提问。
- **自然裂变** — 今日注册且未绑定邀请码的用户。绑定了邀请码的注册计为邀请注册。
- **邀请数据** — 某用户ID 的累计邀请、今日邀请、近7日邀请，一次出齐。
- **团长版本** — V1 / V2 / V3。[ASSUMPTION: 为后台已有团长版本字段。]
- **项目收益** — 某用户ID 的收益。按日区间出按日明细；按年出按月明细；累计只出总值。
- **出单关键词** — 关键词数量，只出数值，不展示具体词。
- **分红** — 某赛道下各项目的总分成与最高分成比例。
- **向上分红关系** — 某用户对其上级的分红关系行：直属、间属、归级、直属团队、间属团队。
- **排名查询** — 赛道下「所有项目各自 Top 3」或「整赛道 Top 3」。
- **关系查询** — 两个用户ID 的直属/间属判定；构不成则回退默认上级。
- **小说类项目** — 小说赛道下的项目集合。已泛化为赛道，不再写死「小说类」。
- **题词量** — 排名查询使用的计数指标。[ASSUMPTION: 计「提词提交次数」，含失败与重复，除非业务另给成功口径。]
- **今日** — 排名查询的默认时间窗。[ASSUMPTION: 业务时区自然日 00:00:00 至当前时刻，时区待业务指定。]
- **用户ID** — 后台主键形态的用户标识，结果表必出。
- **用户昵称** — 用户对外显示名，关系查询必出。
- **直属** — 两人中一方是另一方的默认上级，中间无其他人。
- **间属** — 两人在同一条上级链上，但中间至少隔一层。
- **默认上级** — 每个用户有且仅有一个系统写入的上级。用于直属判定，以及两人无上下级时的回退。
- **团长等级** — 用户在团长体系中的等级字段，关系查询对两个输入用户都要出。
- **暂无数据** — 排名查询中，某小说类项目在今日题词量为 0 时，该项目仍出现，题词量单元格展示的固定文案。

## 4. Features

### 4.1 工作台入口与双栏

**Description:** 运营从管理后台进入独立的 AI工作台，而不是在每个业务页挂一条侧栏。对话区在左，结果区在右，同一屏同时看见「问了什么」和「表是什么」。对标常见企业助手：窄对话负责意图，宽面板负责表格消费（Adobe 全屏助手、C3 侧栏 fully-expanded 看网格是同一逻辑）。Realizes UJ-1, UJ-2.

**Functional Requirements:**

#### FR-1: 进入 AI工作台

运营可以从管理后台打开 AI工作台。Realizes UJ-1.

**Consequences (testable):**
- 具备后台登录态的运营可以到达 AI工作台，未登录被挡在登录流程。
- [ASSUMPTION: 入口为侧栏一级菜单「AI工作台」。]

#### FR-2: 双栏工作面

运营在同一屏使用对话区与结果区。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 对话区在左，结果区在右，默认同时可见。
- 新一次成功查询刷新结果区；对话区保留本轮问答文本。
- 结果区宽度足以阅读至少「用户ID / 项目名称 / 题词量」三列而不必横向猜测列含义。

### 4.2 提问与意图识别

**Description:** 运营用自然语言提问。系统只把语句映射到已支持的查询意图；识别不出或缺关键槽位时，在对话区澄清，不在结果区先出一张可能错的表。v1 允许同构变体（换时间说法、换 Top N、换两个 ID），但不开放任意 NL2SQL。Realizes UJ-1, UJ-2.

**Functional Requirements:**

#### FR-3: 自然语言提交查询

运营可以在对话区输入一句话并提交。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 提交后对话区展示该句原文。
- 空提交不发起查询，结果区保持上一成功结果或初始空态。

#### FR-4: 识别并执行已支持意图

系统将语句识别为已批准查询意图后执行。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 「今天所有小说类业务提词最多的前三名用户」识别为排名查询并执行 §4.3。
- 「查询用户ID1与用户ID2的上下级关系」识别为关系查询并执行 §4.4。
- 「今日自然裂变注册人数」「用户ID累计/今日邀请人数」「今日新增团长人数」「用户ID近7日/30日项目收益」「某某项目今日订单数据」「今日分红数据」分别识别为 §4.7 对应查询。
- 无法归入已批准意图时，对话区说明可问范围并给示例；结果区不填写伪造行。

#### FR-5: 缺槽位时先澄清

关键槽位缺失时，系统先问，再查。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 关系查询缺少任一用户ID：对话区要求补全，不调用关系判定。
- 邀请查询或收益查询缺少用户ID：对话区要求补全。
- 收益查询未指定近7日或近30日：对话区要求补全。
- 订单查询缺少项目名称：对话区要求补全。
- 排名查询缺时间或品类且无法使用默认值：对话区补问。[ASSUMPTION: 「今天」与「小说类」可作为排名查询默认槽位，当语句已包含时不再追问。]

### 4.3 排名查询（小说类各项目题词 Top 3）

**Description:** 种子 Case 1。范围是今日全部小说类项目；每个项目单独按题词量排用户；输出用户ID、项目名称、题词量。同一用户可出现在多个项目。零题词项目仍占一组。并列第 3 全留。Realizes UJ-1.

**Functional Requirements:**

#### FR-6: 按项目输出 Top 3 用户

运营通过排名查询得到每个小说类项目的题词量前三名用户。Realizes UJ-1.

**Consequences (testable):**
- 结果按小说类项目分组；组内按题词量降序。
- 每组默认最多 3 名用户，除非触发 FR-8 并列规则。
- 每行包含用户ID、项目名称、题词量。
- 同一用户ID 可以出现在多个项目组。

#### FR-7: 零题词项目仍展示

今日题词量为 0 的小说类项目仍出现在结果区。Realizes UJ-1.

**Consequences (testable):**
- 该项目分组可见。
- 题词量位置展示「暂无数据」，不省略该项目。

#### FR-8: 并列第 3 全留

与第 3 名题词量相同的用户全部留下。Realizes UJ-1.

**Consequences (testable):**
- 若第 3 名题词量为 N，所有题词量 ≥ 该组第 3 名阈值且排在前三档的用户都出现；并列第 3 可使该组超过 3 行。
- 排序稳定：题词量相同的行仍全部展示，不静默丢弃。

### 4.4 关系查询（两人上下级）

**Description:** 种子 Case 2。先判定两个用户ID 是否构成直属或间属，并给出方向、双方团长等级、用户昵称。每个用户有且仅有一个默认上级。两人构不成上下级时（分叉、不在同一条链），分别给出各自的默认上级，不铺整条祖先链，也不宣称「全站任意两人必有上下级」。Realizes UJ-2.

**Functional Requirements:**

#### FR-9: 判定直属或间属

运营输入两个用户ID 后，系统判定是否存在上下级及方向。Realizes UJ-2.

**Consequences (testable):**
- 一方是另一方的默认上级：结果为直属，并写明谁是谁的上级。
- 一方在另一方的上级链上且中间至少隔一层：结果为间属，并写明谁是谁的上级。
- 同时给出两个输入用户的用户ID、用户昵称、团长等级。

#### FR-10: 无上下级时回退默认上级

两人构不成直属或间属时，分别返回各自的默认上级。Realizes UJ-2.

**Consequences (testable):**
- 结果区明确写「这两人无上下级关系」。
- 各出一行：输入用户ID → 其默认上级的用户ID，并带双方用户昵称、团长等级。
- 不展开默认上级之上的祖先。

#### FR-11: 用户不存在或 ID 非法

输入无法对应到用户时，不编造关系。Realizes UJ-2.

**Consequences (testable):**
- 对话区指出哪个用户ID 无效或不存在。
- 结果区不生成直属/间属结论。

### 4.7 三类盘点查询

**Description:** 已批准问法归为项目业务、用户数据、用户关系。口径写死在意图里。

**Functional Requirements:**

#### FR-17: 赛道下所有项目今日题词 Top 3

运营按赛道查询其下每个项目的今日用户题词 Top 3。输出用户ID、用户昵称、项目名称、题词量。每项目单独排名；零题词「暂无数据」；并列第 3 全留。

#### FR-18: 赛道下今日用户题词 Top 3

运营按赛道查询整赛道（非单项目）今日用户题词 Top 3。输出列同 FR-17。

#### FR-19: 赛道下今日分红

运营按赛道查询今日分红。每行：项目名称、总分成、最高分成比例。

#### FR-20: 指定项目按日订单

运营查询某项目的按日订单。每行：项目名称、出单人数、出单关键词数量、订单量、累计收益。关键词只出数量。

#### FR-21: 用户邀请数据

运营按用户ID 一次查出累计邀请、今日邀请、近7日邀请。

#### FR-22: 今日注册人数

运营查询今日累计注册、自然裂变注册、邀请注册。未绑邀请码 = 自然裂变。

#### FR-23: 今日升级团长数

运营查询今日升级为 V2、V3 的团长人数。

#### FR-24: 团长身份数据统计

运营查询当前 V1 / V2 / V3 团长人数。

#### FR-25: 用户项目收益

运营按用户ID 查询近7日、近30日、日期范围、累计或某年项目收益。必出用户ID 与累计收益。按日区间出按日明细；按年出按月明细。

#### FR-26: 用户向上分红关系

运营按用户ID 查询向上分红关系（可按日 / 累计 / 日期）。每行：用户ID、关系（直属、间属、归级、直属团队、间属团队）、上级ID、累计分红。

#### FR-27: 用户在指定项目上的向上分红

运营按用户ID + 一个或多个项目名称，查询这些项目收益向上产生的分红。每行：项目名称、用户ID、关系、上级ID、累计分红、今日分红、昨日分红。缺用户ID 或项目名称时先澄清。

### 4.5 结果区展示

**Description:** 答案在右侧。对话区最多一句人话结论（例如「已按 12 个小说类项目列出今日题词榜」），完整字段在结果区。运营要的是能抄的表，不是一段解释性散文。Realizes UJ-1, UJ-2.

**Functional Requirements:**

#### FR-12: 右侧出表且可复制用户ID

运营可以在结果区阅读表格并复制用户ID。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 排名查询结果区为分组表，列至少为用户ID、项目名称、题词量。
- 关系查询结果区为关系结论 + 用户字段表（用户ID、用户昵称、团长等级，以及默认上级回退时的上级用户ID）。
- 用户ID 可被选中复制。

**Out of Scope:**
- 点击用户ID 跳转原后台详情页（v1 不阻塞，见 §6.2）。
- 导出 Excel / 分享链接。

#### FR-13: 查询进行中与失败态

查询未完成或失败时，结果区状态明确。Realizes UJ-1, UJ-2.

**Consequences (testable):**
- 执行中展示加载态，不沿用上一张表冒充本次结果。
- 失败时对话区给失败原因（权限不足 / 超时 / 服务不可用），结果区保持可辨认的失败空态。

### 4.6 只读、权限与审计

**Description:** 第一刀只查不做。数据范围不超过该运营在原后台已有的权限。查询过程可追溯，便于对错数、对滥用。Realizes UJ-1, UJ-2.

**Functional Requirements:**

#### FR-14: 只读，不代操作

系统不得因对话内容改写业务数据。

**Consequences (testable):**
- 即使运营写出「把用户ID1 的上级改成用户ID2」，系统不执行写操作，并在对话区拒绝。
- v1 无任何「代操作」确认流。

#### FR-15: 权限不放大

运营只能看到其原后台权限内的项目与用户字段。

**Consequences (testable):**
- 无权项目不出现在排名查询分组中，或整查询因权限不足失败（二选一须在实现前由权限模型定案）。[ASSUMPTION: 无权项目直接不出现在分组中，对话区注明「已按你的权限过滤」。]
- 无权查看的用户ID 按 FR-11 同类处理：不泄露昵称与团长等级。

#### FR-16: 查询可追溯

系统记录每次查询的提问原文、识别出的查询意图、执行时间与操作者。

**Consequences (testable):**
- 管理侧可按运营、时间查出该次提问与意图类型。
- 记录不含把完整结果表永久铺成可被无关人员检索的开放日志。[ASSUMPTION: 审计留提问、意图、时间、操作者、成功/失败；结果快照是否落库由架构定，PRD 不强制。]

## 5. Non-Goals (Explicit)

- 不做通用「问任意 SQL / 扫全库」聊天机器人。
- 不做 AI 代操作（改绑、调账、发奖、改配置）。
- 不做开放式分析（漏斗、趋势图、归因、自动写周报）。
- 不在每个业务菜单嵌入悬浮助手；v1 只有独立 AI工作台。
- 不替代原有菜单与列表页；原路径仍可用。
- 不对 C 端用户开放。

## 6. MVP Scope

### 6.1 In Scope

- 管理后台内的 AI工作台双栏（对话区 + 结果区）。
- 已批准查询意图分三类：项目业务（赛道分项目/整赛道题词 Top 3、赛道分红、项目按日订单）、用户数据（邀请、今日注册、升级团长、团长身份、项目收益）、用户关系（两人上下级、向上分红关系、指定项目向上分红）。
- 空项目「暂无数据」、并列第 3 全留、无上下级时回退默认上级。
- 只读、权限不放大、基础查询审计。
- 缺槽位澄清与不支持意图的拒绝话术。

### 6.2 Out of Scope for MVP

- 未列入已批准清单的开放式问法（仍禁止任意 NL2SQL）。
- AI 代操作与写确认流。
- 从结果区跳转用户/项目原页、导出、会话历史跨设备同步。[NOTE FOR PM: 跳转原页是运营可能立刻要的增强，验证期如果复制 ID 仍频繁切菜单，优先加。]
- 图表、语音输入、移动端。
- 自定义指标口径配置台（运营自己定义「题词量」公式）。

## 7. Success Metrics

运营问询频率未知，v1 先测「问得对、数得准、少切菜单」，不测热闹程度。

**Primary**
- **SM-1**：种子 Case 金标准一致率 — 用固定题库（至少覆盖：多项目有数、零题词项目、并列第 3、直属、间属、无上下级回退、非法 ID）跑排名查询与关系查询，字段级一致率 100%。验证 FR-6–FR-11。
- **SM-2**：运营完成一次种子任务的中位耗时，对比原跨菜单路径下降。[ASSUMPTION: 基线由 3–5 名运营各走一遍原路径测得；无基线则先报工作台绝对耗时。] 验证 FR-1–FR-3, FR-12。

**Secondary**
- **SM-3**：澄清率 — 种子问法（完整槽位）首次提交即执行、不进入澄清的比例 ≥ 95%。验证 FR-4, FR-5。
- **SM-4**：周活跃运营人数（进了 AI工作台并成功出表）。只作健康度，不作达标KPI。

**Counter-metrics (do not optimize)**
- **SM-C1**：对话区字数 / 「AI 回复很长」——加长解释不能替代结果区表。对冲 SM-3。
- **SM-C2**：查询次数本身 — 同一问题反复重问可能说明数不可信。对冲 SM-4。

## 8. Information Architecture

- **Surface：** 桌面 Web 管理后台，≥1280px 为设计基准。
- **导航：** 独立一级入口进入 AI工作台；进入后主区为双栏，不再套一层顶 Tab。
- **对话区：** 输入框、本轮消息、澄清问句、一句结论。
- **结果区：** 当前查询的表、加载、失败、初始引导（两类示例问法）。
- **非 v1：** 历史会话列表、把工作台挂到礼品中心等业务页。

## 9. Cross-Cutting Requirements

### 9.1 NFRs

- **正确性：** 题词量与上下级必须由业务库/既有判定逻辑得出，禁止模型口算排名或 invent 一条链。
- **时延：** [ASSUMPTION: 种子查询 P95 < 8s；超时走 FR-13。]
- **可用性：** 与管理后台同域、同登录态，不另开一套账号。
- **可观测：** 记录意图识别结果、耗时、失败码，便于对 SM-1 / SM-3。

### 9.2 Constraints and Guardrails

- **安全：** 只读。提示词或用户输入不得升级为写库、导出全表、绕过权限。
- **隐私：** 结果区仅出本查询需要的用户ID、用户昵称、团长等级及关系字段，不附带手机号、实名、钱包余额等未点名字段。
- **成本：** v1 用已批准意图 + 受控查询，不用「每句任意生成 SQL」。

### 9.3 Integration and Dependencies

- 依赖现有项目品类（小说类项目）、题词量事实表/事件、用户默认上级与团长等级。
- 依赖管理后台登录与权限模型。
- 具体存储、模型、编排放 `addendum.md`，不在本 PRD 选型。

### 9.4 Data Governance

- 用户ID、用户昵称、团长等级按后台既有数据分级处理。
- 不把对话拿去训练公有模型。[ASSUMPTION: 若已有公司 LLM 数据政策，本工作台遵守同一套。]

### 9.5 Risks

- **错数被当成真相：** 用 SM-1 金标准门禁，结果区展示查询时间窗与品类。
- **运营以为能改数据：** FR-14 明确拒绝写指令。
- **「任意两人都有关系」被做错：** FR-10 采用分叉回退，禁止做成单根树幻想。
- **范围膨胀：** 新 Case 必须能归入已有查询意图或单独立项，禁止静默加开放 NL2SQL。
