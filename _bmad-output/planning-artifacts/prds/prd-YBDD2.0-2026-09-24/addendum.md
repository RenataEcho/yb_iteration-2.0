## 实际累计：读哪一笔钱

用户原话是「领取稿件关联的关键词累计产生的收益」。与 FR-014 对齐后：

- 必须已回填才是代发关键词，否则「领取」还没绑死。
- 「产生的收益」按 **应结算（拆账前订单收益）** 读，池子更大，营销上说得通；若改成只加用户实结，池子变小、和剪辑手侧叙事不一致。
- 待结算排除：池子否则会回撤，公开数字回撤比偏小更伤信任。

不另建入账行。池子是只读投影 + 虚拟加数。

## 活动次数为什么不并进免费次数

免费次数跨日按工作日 / 节假日重置。若把抢到的次写进免费剩余，第二天会被重置冲掉，黏性活动变成日清彩票，也污染次数商品页上的两个字段。独立桶才能「额外再给」且不改历史次数商品页。

扣次顺序起草为 免费 → 活动 → 已购：先消耗每天会重置的，再消耗活动，最后动积分买来的。若运营要「先逼人用掉活动次数」，可改成 活动 → 免费 → 已购，属 Open Question 3。

## 为什么不改历史页面

迭代需求以 FR Demo 页为溯源单元。在 `fr-opc-yijian-daifa.html` 或 `yijian-daifa-demo.html` 上打补丁，会出现：

- 旧 FR-014 验收面和新规则叠在同一文件，diff 无法回答「这是哪一刀」。
- 卡片不展示金额的合同被一处「顺便加数字」破坏。
- 活动中心（FR-006）领取按钮语义是资料 / 跳转，不是次数桶。

因此本迭代作品广场、新活动页、新后台配置页与新 `fr-xxx` 壳一起开。不单开首页。线上真广场要接池子，另开变更。

## 弃选

- 单开首页承载收益池 / 限时领次：用户已改口为都在作品广场露出。
- 在作品广场卡片 / 详情露出金额：与 FR-014 明确冲突。池子挂广场顶部，不是单稿金额。
- 把限时领做成积分兑换的又一个档位：用户已改口为额外再给、先到先得，不扣积分。
- 替换工作日 / 节假日自动免费：用户要的是叠加。
- 复用活动中心历史页当唯一容器：改历史页，溯源差；活动中心也没有次数账。
- 更新 AI 工作台 PRD：用户禁止。

## 可比做法（Discovery 未跑完检索，仅作起草背景）

公开「已发放 / 已赚」大数：内容平台常用种子数 + 真实累加；风险是用户把大数认成自己的余额。每日前 N 名：秒杀式库存，失败态必须可解释，超发是事故。这两条已收进 PRD 的 counter-metrics 与 FR-8。

## 不进 PRD 的机制

- 库存扣减用服务端原子计数 / 券码池，禁止信客户端。
- 实际累计可物化日增量，按关键词订单已结算事件更新。
- 本迭代 Demo 继续假数据，不接真积分、真支付。
