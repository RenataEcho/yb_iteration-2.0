# PRD: 一键代发增量 — 收益池露出与限时领次

本文件只覆盖一键代发这一刀增量。不更新、不并入 `_bmad-output/planning-artifacts/prds/prd-YBDD2.0-2026-09-03/` 的 AI 工作台 PRD。

## 0. Document Purpose

给产品、UX、架构和后续 SPEC / Epic 使用。词汇以 §3 为准。本文 **FR-n** 只表示本增量第 n 条，不是全库全局编号；迭代需求页编号为 **FR-017**。已拍板口径见 §13；未决只留 §12。

底座合同是 `_bmad-output/specs/spec-fr014-yijian-daifa/`（FR-014-01 … FR-014-32）。本 PRD 不重写那份合同，只定义两件新事：代发收益池和限时领次都在作品广场露出，以及额外次数的限时领次活动。不单开首页。交付按右豹迭代需求：新开本迭代广场页，不改历史广场文件。下游更新 FR-014「剩余次数 = 免费 + 已购」字面时，以本文件三桶为准，不要回改历史 Demo 页。

## 1. Vision

一键代发已经能领、能发、能按分成入账，但用户在作品广场上看不见「这件事值多少」。稿件卡片、详情、领取列表按合同不展示金额，价值只能靠分成比例和口头说明，营销上弱。

这一刀把领取稿件关联关键词累计产生的收益做成全员可见的代发收益池，挂在作品广场顶部；限时领次入口也挂在同一页。让人刷稿时一眼看见代发在赚钱，并能当场去抢额外次数。不单开首页。

试点只验这两件事是否说得清、抢得成、账不算乱。不改历史广场文件、不把金额写进卡片、不把活动中心或次数商品页推倒重来。

## 2. Target User

### 2.1 Jobs To Be Done

- **功能**：打开作品广场就看到代发收益池和限时领次入口；在限时窗内领到额外领取次数，回广场领稿。
- **情境**：有项目、有词、自己不做片；每天进来会看有没有便宜次数。
- **情绪**：觉得代发是真能赚的，不是空广场；抢到次数有赚到，没抢到也知道为什么。
- **社交**：可以把公开的池子数字当卖点转给同行，不必解释后台怎么分账。
- **运营**：能调虚拟配置把池子先撑起来，能开一档每天抢次的活动，而不去改已经定稿的历史页。

### 2.2 Non-Users (v1)

- 剪辑手（本增量不改 PC 看板、不改剪辑手收益页）。
- 只想在稿件卡片或稿件详情上看见金额的人——卡片与详情本增量仍不展示金额。收益池是广场顶部模块，不是单稿金额。
- 要用积分买这次活动名额的人——本增量是额外再给，不扣积分。
- 未登录访客、无 App 权限的人。
- 需要改 AI 工作台、代发分配（FR-001）、代发收益主子协议（FR-002）的角色。

### 2.3 Key User Journeys

试点、C 端营销向。具名场景四条。主人公沿用 C 端领取用户画像，不单独立人设文档。

- **UJ-1. 林晓在作品广场看见代发收益池，决定去领稿。**
  - **Persona + context:** 林晓，26 岁，有品牌项目和已通过的词，会发抖音，自己不做片。
  - **Entry state:** 已登录；打开的是本迭代作品广场，不是历史广场文件，也不是单独首页。
  - **Path:** 看见广场顶部代发收益池的展示收益 → 读懂这是领取稿件关联关键词累计产生的收益 → 继续刷下方宫格领稿。
  - **Climax:** 她相信代发值一做，而不是只看到空宫格。
  - **Resolution:** 人仍在广场，领取次数仍按现有门禁走。卡片不展示金额。
  - **Edge case:** 实际累计还是 0、只靠虚拟配置撑着时，她看到的仍是一个正数；后台能拆出虚拟配置与实际累计。

- **UJ-2. 林晓每天从广场打开限时领次活动，抢到额外次数。**
  - **Persona + context:** 同上；当天免费次数不够用，又不想先花积分兑次数商品。
  - **Entry state:** 已登录；从作品广场活动条进入本迭代限时领次页。
  - **Path:** 看到今日还剩可领名额与活动时间 → 点领取 → 活动次数入账 → 领取次数合计增加。
  - **Climax:** 她知道多了几次，可以回广场领。
  - **Resolution:** 作品广场 / 稿件详情仍只出示领取次数合计，不拆三桶。历史广场文件不改。
  - **Edge case:** 名额抢完或剩余每日发放量不够发一整份，页上是售罄，引导改天再来或走既有次数商品，不改详情兑换浮层。

- **UJ-3. 林晓来晚了，或活动未开。**
  - **Persona + context:** 同 UJ-2。入口仍是本迭代限时领次页。
  - **Entry state:** 活动未开始、已结束、今日可领名额为 0，或剩余每日发放量小于每次发放的活动次数。
  - **Path:** 进入限时领次页 → 领取不可用 → 看清原因。
  - **Climax:** 失败可解释，不误扣、不超发。
  - **Resolution:** 免费次数与已购剩余不动。

- **UJ-4. 赵敏配池子和当天抢次，且只在新页上操作。**
  - **Persona + context:** 赵敏，运营，要在试点期把池子数字和每日抢次调到能讲故事。
  - **Entry state:** 右豹后台，本迭代新配置页；不打开 FR-014 次数商品页改历史字段。
  - **Path:** 写入虚拟配置 → 看到实际累计与展示收益 → 配置每日发放量、可领名额、每次发放的活动次数、活动时间窗 → 发布。
  - **Climax:** C 端本迭代作品广场和新活动页立刻按新配置演。
  - **Resolution:** 历史广场文件外观与规则文案不变，溯源时能指出「这是 FR-017 的页」。

## 3. Glossary

下游必须用这些词。§4 新出现的名词已收在这里。FR-014 已定义且本文件沿用的词，含义不变。

- **一键代发** — 剪辑手供稿、用户领取后发布变现。不是 FR-001 代发分配，不是 FR-002 代发收益。
- **用户** — 无剪辑制作能力、靠领取稿件做项目变现的领取方。
- **稿件** — 剪辑手上传并发布到平台的内容单元。
- **作品广场** — 用户浏览可领取稿件的宫格页。本增量在**本迭代广场页**顶部挂代发收益池和限时领次入口；稿件卡片仍不展示金额。历史广场文件不改。
- **稿件详情** — 单条稿件页。本增量不改此页，也不在此页展示金额。
- **用户领取页** — 用户查看自己已领取记录的页面。本增量不改此页。
- **关键关键词** — 用户自主申请的词；领取时必须先选词。
- **代发关键词** — 存在至少一条已回填绑定 `(keywordId, claimId)` 的词。未回填 / 已超时不构成绑定。
- **领取次数** — 用户可成功领取稿件的剩余配额。本增量起 = 当日免费剩余 + 已购剩余 + 活动剩余。
- **免费次数** — 后台按工作日 / 节假日配置的免费领取额度；跨自然日重置免费剩余，已购不重置。本增量不改其配置页与重置规则。
- **次数商品** — 「x 次需要 y 积分」档位。本增量不改此商品、不改兑换浮层。
- **已购剩余** — 用户用积分兑换次数商品后尚未用掉的次数。
- **活动次数** — 用户从限时领次活动领到、尚未用掉的次数。额外再给，不扣积分。
- **活动剩余** — 当前未用完的活动次数。
- **用户收益入账** — 关键词订单转为已结算时写入既有项目收益明细的拆账。广场 / 详情 / 领取列表仍不展示金额。
- **代发收益池** — 给所有已登录用户看的公开累计收益，挂在作品广场顶部做营销，不是某一用户的可提现余额，也不是项目收益明细的另一行，也不是单稿金额。
- **实际累计** — 代发收益池里按账算出来的部分：已回填代发关键词上、已结算订单的应结算金额合计。应结算 = 写入用户收益入账前的订单收益（用户实结 + 剪辑手分账）。待结算不计入。一词多条已回填时，池子仍按该词全部已结算应结算加总，不改成「只加最近一条 claim」。
- **虚拟配置** — 运营写入的营销加数，只进入展示收益，不写入用户收益入账，不进剪辑手分账。
- **展示收益** — 作品广场代发收益池出示的数字。展示收益 = 虚拟配置 + 实际累计；虚拟配置 ≥ 0。
- **限时领次活动** — 在免费次数与次数商品之外，按时间窗发放活动次数的活动。每天有每日发放量，前若干名可领，先到先得。
- **每日发放量** — 一个自然日内，该限时领次活动最多发出的活动次数总量。
- **可领名额** — 一个自然日内，最多多少名用户能领到。每名用户每个自然日在同一限时领次活动中最多成功领取 1 次。
- **每次发放的活动次数** — 一名用户一次成功领取时得到的活动次数。运营配置，正整数，默认 1。
- **历史页面** — 本增量开始前已经存在的迭代 Demo / 需求页，包括但不限于 `fr-opc-yijian-daifa.html` 及其 C 端广场 / 详情 / 领取 / 次数商品场景、`yijian-daifa-demo.html`、`fr-activity-center.html`。
- **本迭代页** — 为本增量新开的迭代需求记录页（FR-017）及其本迭代作品广场、限时领次、新后台场景。验收与溯源只认本迭代页。不单开首页。
- **试点** — 本增量先按可开关配置验收，全员可见、全员可抢，不做白名单；不把规则补丁打进历史页面。

## 4. Features

### 4.1 代发收益池露出

**Description:** 所有已登录用户在本迭代作品广场看到同一个代发收益池。数字来自虚拟配置加实际累计，用来讲「领稿能产收益」，不用来当个人钱包。不改历史广场文件，不破稿件卡片 / 详情 / 用户领取页的金额禁令。不单开首页。实现 UJ-1、UJ-4。

**Functional Requirements:**

#### FR-1: 全员可见代发收益池

已登录用户在本迭代作品广场看到代发收益池。试点全员，不做白名单。未登录隐藏整模块。实现 UJ-1。

**Consequences (testable):**
- 任意两个已登录用户同一时刻看到的展示收益相同。
- 代发收益池不是可点提现、不是个人项目收益明细入口。
- 本迭代广场的稿件卡片、稿件详情、用户领取页仍不展示金额。
- 历史广场文件 `fr-opc-yijian-daifa.html` / `yijian-daifa-demo.html` 相对本增量零 diff。

#### FR-2: 实际累计口径

系统按领取稿件关联的关键词计算实际累计。实现 UJ-1。

**Consequences (testable):**
- 只计入代发关键词（已回填绑定）上、状态为已结算的订单应结算金额。
- 未回填、已超时、先结算后回填且合同规定不回溯的订单，不计入。
- 站外稿、非代发关键词的全额用户收益，不计入。
- 应结算 = 该笔订单写入用户收益入账前的订单收益（用户实结 + 剪辑手分账）；待结算不计入。
- 实际累计只增不改历史入账行；改分成比例不重算已计入的实际累计。

#### FR-3: 虚拟配置

运营在本迭代新后台页写入虚拟配置，非负。实现 UJ-4。

**Consequences (testable):**
- 虚拟配置不产生用户收益入账，不进项目收益明细，不进剪辑手分账。
- 后台同时出示虚拟配置、实际累计、展示收益三数。
- 虚拟配置每次保存留审计（谁、何时、新旧值）。
- 历史次数商品页、FR-014 后台七页不因本能力改字段或改布局。

#### FR-4: 展示收益合成

作品广场代发收益池只出示展示收益一个数。实现 UJ-1。

**Consequences (testable):**
- 展示收益 = 虚拟配置 + 实际累计。
- C 端不拆「其中虚拟 / 其中实际」，也不加「含预估」一类合成话术。
- 展示收益不得小于实际累计（虚拟配置 ≥ 0）。
- 不披露带来的造假观感用 SM-C2、SM-C4 观察，不靠改 C 端文案对冲。

#### FR-5: 作品广场模块，不单开首页

代发收益池和限时领次入口都出现在本迭代作品广场。不单开首页。实现 UJ-1。

**Consequences (testable):**
- 存在独立的本迭代作品广场场景，顶部含代发收益池模块和限时领次入口，下方仍是稿件宫格。
- 历史广场文件与场景不被修改。
- 不另做独立首页来承载池子或活动。

**Out of Scope:**
- 按项目、按剪辑手、按用户拆池。
- 在作品广场卡片上展示金额。

### 4.2 限时领次活动

**Description:** 运营开一档限时领次活动：每天放出每日发放量，可领名额有限，先到先得。用户领到的是活动次数，加进领取次数，不替代免费次数，不走次数商品，不扣积分。实现 UJ-2、UJ-3、UJ-4。

**Functional Requirements:**

#### FR-6: 活动次数独立桶

活动次数与免费次数、已购剩余分桶。实现 UJ-2。

**Consequences (testable):**
- 领取次数 = 当日免费剩余 + 已购剩余 + 活动剩余。
- 跨自然日重置免费剩余时，活动剩余与已购剩余不因该重置清零。
- 领取稿件成功扣 1 次，不退。扣次顺序：免费剩余 → 活动剩余 → 已购剩余。
- 超时释放、未回填，不退活动次数。
- 次数商品兑换、工作日 / 节假日免费额度的配置与计算不变。

#### FR-7: 活动配置

运营在本迭代新后台页配置限时领次活动。实现 UJ-4。

**Consequences (testable):**
- 可配置：活动时间窗、每日发放量（≥ 0）、可领名额（≥ 0）、每次发放的活动次数（正整数，默认 1）。
- 试点只支持同时进行 1 档限时领次活动。
- 关停或过期后，已领到的活动剩余保留，只是不能再领新的。
- 不把这些字段写进历史次数商品页。

#### FR-8: 先到先得领取

已登录且未停权的用户，在活动进行中、本人当日尚未领过、剩余可领名额 ≥ 1、且剩余每日发放量 ≥ 每次发放的活动次数时，领取成功。实现 UJ-2、UJ-3。

**Consequences (testable):**
- 成功：该用户当日记已领；活动剩余 + 每次发放的活动次数；可领名额 − 1；每日发放量 − 每次发放的活动次数。
- 两条上限独立：成功人数 ≤ 可领名额；发出的活动次数总和 ≤ 当日每日发放量。
- 失败不扣任何桶、不记已领：可领名额 < 1、剩余每日发放量 < 每次发放的活动次数、未开始、已结束、当日已领过、未登录、已停权。
- 不扣积分，不打开次数商品兑换浮层。

#### FR-9: 活动页状态

本迭代限时领次页必须让用户看懂现在能不能领。实现 UJ-2、UJ-3。

**Consequences (testable):**
- 至少区分：未开始、进行中可领、进行中已领、进行中售罄、已结束。
- 进行中售罄包含：可领名额为 0，或剩余每日发放量 < 每次发放的活动次数。
- 进行中出示剩余可领名额或等价售罄态。
- 入口做在本迭代作品广场。历史活动中心页不被修改，也不作为本活动的入口。不单开首页。

#### FR-10: 与领取门禁兼容

用户拿着活动次数去领稿时，仍走 FR-014 门禁：停权 → 次数 → 选词 → 资格 / 占用。实现 UJ-2。

**Consequences (testable):**
- 次数门禁读领取次数合计；合计 > 0 不得因「免费剩余为 0」单独拦下。
- 历史详情 Demo 文件不改。线上次数门禁与剩余数字读领取次数合计，属于接口口径，不作为改历史页。
- 次数不足时仍只打开既有兑换浮层；浮层本身不改。

### 4.3 迭代交付与溯源

**Description:** 这一刀是新的迭代需求。改历史页面会把旧 FR 的验收面和新规则搅在一起，溯源失败。实现 UJ-4。

#### FR-11: 只新开本迭代页

本增量的 C 端与后台验收面全部落在本迭代页。

**Consequences (testable):**
- 新增独立迭代需求记录页 FR-017，含本迭代作品广场、限时领次、新后台配置场景。
- 下列历史页面在本增量中零 diff：`fr-opc-yijian-daifa.html` 及其已挂 C 端 / PC / 后台场景、`yijian-daifa-demo.html`、`fr-activity-center.html`、`fr-opc-daifa-allocation.html`、`fr-opc-daifa-revenue.html`、AI 工作台相关页。
- 规则抽屉只写本增量条款，不把 FR-014-01 … FR-014-32 抄一遍。

#### FR-12: 历史页行为保持

即使线上将来要把代发收益池接到真实历史广场，本增量的需求与 Demo 仍以本迭代广场页为准，不回改历史页来「顺便加上」。

**Consequences (testable):**
- 评审与验收对照本迭代广场页，不对照被改过的历史页截图。
- 需要接真实历史广场时，另开变更，不在本 PRD 范围里改历史页。
- 不另做独立首页来承接本增量。

## 5. Non-Goals (Explicit)

- 不更新 AI 工作台 PRD，不把本增量写进那份文档。

## 8. Ledger Boundaries

三套旧账继续有效。本增量只多两样：**展示用的代发收益池**，以及 **领取次数里的活动剩余**。

| 账 | 写入 | 谁看见金额 / 次数 | 本增量 |
| --- | --- | --- | --- |
| 用户收益入账 | 已结算关键词订单按分成快照拆到项目收益明细 | 用户 / 剪辑手在既有明细里看；广场等列表不展示金额 | 不改写入。实际累计只读已结算应结算 |
| 免费次数 | 工作日 / 节假日配置，跨日重置 | 详情底栏合计里的一部分 | 不改配置与重置 |
| 次数商品 / 已购剩余 | 积分兑换 | 同上；兑换浮层不改 | 不改商品 |
| 代发收益池 | 虚拟配置 + 只读实际累计 | 全员在作品广场看展示收益 | 新增；不是可提现 |
| 活动次数 | 限时领次活动先到先得 | 新活动页；合计并入领取次数 | 新增；额外再给 |

关系钉死如下：

1. 代发收益池 **不是** 用户收益入账的汇总行，也 **不是** 某一用户的余额。
2. 虚拟配置 **永不** 写入项目收益明细。
3. 实际累计的订单集合 ⊆ 已回填代发关键词的已结算订单；与入账拆账同源，但不给用户多记一笔。
4. 活动次数 **不是** 免费次数，跨日不按节假日规则重置。
5. 活动次数 **不是** 次数商品，领取不扣积分。
6. 作品广场卡片仍然不展示金额——代发收益池活在广场顶部模块，不写进单稿。

## 9. Constraints and Guardrails

- **溯源：** 禁止为了「方便接上」而改历史页面。线上真广场若要接池子，另开变更。不单开首页。
- **信任：** 展示收益可以含虚拟配置，但后台必须能拆开；禁止用虚拟配置冒充单笔用户收益入账。C 端不披露合成方式。
- **公平：** 先到先得必须防超发；售罄后不得靠重试领到。可领名额与每日发放量分开扣。
- **门禁：** 不颠倒 FR-014 领取门禁顺序。
- **钱与次分离：** 代发收益池是营销数字；领取次数是配额。两者不能互相折算。

## 11. Cross-Cutting NFRs

- **正确性：** 活动次数超发事故 = 0；展示收益在虚拟配置变更后的下一拉必须一致。
- **时效：** 实际累计允许短延迟，广场最长 15 分钟陈旧；虚拟配置与活动开关保存后，下一次打开作品广场 / 活动页必须已生效。
- **可观测：** 记录虚拟配置变更、活动领取成功 / 失败原因、当日已发量与已用名额。
- **安全：** 领取接口鉴权；禁止客户端上报「我领到了」当准。
- **无障碍：** 展示收益与剩余名额用文本数字，不单靠色块。
