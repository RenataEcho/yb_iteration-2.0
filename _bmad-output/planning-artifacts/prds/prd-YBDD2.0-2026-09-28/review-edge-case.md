## Findings

### EC-1 书已领取后，同书剩余关键词再下发

- **location:** §3「剪辑任务」；FR-3「下发只作用于这一条关键词」；FR-4「还没下发的词不在这次领取里」「领走之后其他人仍能看见这本书，但不能再领」；UJ-2 Path「这本书下每个已下发关键词任务都归他」
- **trigger_condition:** 书下部分词已下发并被剪辑手领取；之后运营再下发该书其余关键词
- **why_unhandled:** 合同只定义「领取当下已下发的词归领取人」，未定义领取之后新下发词的归属：自动挂给原领取人、形成可被第三人领取的新池、还是永久悬空
- **consequence:** 实现者若选自动挂靠，与「领取时快照」字面冲突；若悬空，则已领书不能再领、新词无人可领，任务永久卡死

### EC-2 任务池卡片关键词数与领取后任务列表不同步

- **location:** FR-4「关键词数量是这本书已经下发、可供领取的关键词任务数」；FR-4「这本书下这些已下发的关键词任务全部领取成功」；FR-5「任务稿件只列出…已领取的关键词任务」
- **trigger_condition:** 卡片展示的关键词数量与领取成功后任务稿件行数不一致（含 EC-1 后下发、或领取过程中并行下发）
- **why_unhandled:** 未规定领取瞬间是否锁定数目、领取后卡片数量是否冻结、任务稿件是否允许出现多于/少于领取时卡片数的行
- **consequence:** 前端/后端各算各的「已下发」集合，验收无法判定领取是否成功、少任务属缺陷还是预期

### EC-3 两名剪辑手同时领取同一本书

- **location:** FR-4「一个平台关键词只被这一名剪辑手领走」「领走之后其他人…不能再领」
- **trigger_condition:** 两名剪辑手在书仍显示未领取时几乎同时点抽屉内「领取」
- **why_unhandled:** 只写终态互斥，未写并发冲突时的拒绝、回滚、谁成功、失败提示与重试后卡片态
- **consequence:** 双写归属或双成功后一方无任务可传，收益归属剪辑手无法唯一确定

### EC-4 已领一书的剪辑手再领第二本书

- **location:** FR-4「一名剪辑手只领取一本书」「已经领过一本书的剪辑手，不能再领另一本书」；UJ-2 Resolution 同义
- **trigger_condition:** 剪辑手已成功领取书 A，再对书 B 打开抽屉点领取
- **why_unhandled:** 禁止已写，但未写失败表现（按钮禁用、提交后报错文案、书 B 是否仍显示可领）及与「所有人可见」展示的交叉
- **consequence:** 实现者自行发明交互；有的入口仍可点导致误点后无反馈，验收口径分裂

### EC-5 剪辑手从未领取时任务稿件为空

- **location:** FR-5「任务稿件只列出当前登录剪辑手已领取的关键词任务」「没领取的书，其任务不出现」；§11 已确认同义
- **trigger_condition:** 剪辑手登录任务稿件且名下领取数为 0
- **why_unhandled:** 未写空列表是否合法、是否展示空态文案、表上方统计是否全 0、批量上传入口是否仍可用、查询后清空是否仍为空
- **consequence:** 实现者可能当成异常态做引导页或隐藏 Tab，与「只显示已领取」合同被改写成「必须先有任务才进页」

### EC-6 未领取前上传 / 对未出现在任务稿件中的任务上传

- **location:** UJ-2 Edge「没领的书…也不能上传」；FR-5「没出现在他任务稿件里的任务不能上传」；批量「自动匹配这名剪辑手已领取、还没上传的任务」
- **trigger_condition:** 剪辑手未领该书，却通过直达链接、伪造任务 ID、或批量文件夹关键词名撞上未领取任务试图上传
- **why_unhandled:** 禁止已写，未写拒绝通道（前端隐藏即止 vs 服务端强校验）、错误提示、以及批量匹配到「他人已领 / 无人领」时是跳过还是报错
- **consequence:** 仅靠 UI 隐藏会被绕过；批量静默跳过与报错两种实现导致运营以为上传成功实则漏稿

### EC-7 任务稿件「删除这一行」后的归属与再可见性

- **location:** FR-5「操作可以删除这一行，删除后不再出现在任务稿件里」；管理后台「操作是详情、编辑、删除」；FR-4 领取后他人不能再领
- **trigger_condition:** 剪辑手或运营删除任务稿件中的一行（未上传 / 已上传 / 已上架广场 任一）
- **why_unhandled:** 未区分删的是「展示行」「稿件」「领取关系」还是「关键词任务」；未写删除后该书/该词是否释放、原剪辑手是否仍占「一书名额」、广场稿件与分成链路是否失效
- **consequence:** 实现者猜「软隐藏」则僵尸占用一书名额；猜「释放任务」则与一书一领终态冲突；已领用户侧稿件可能突然不可下载

### EC-8 查询清空后行集：剪辑手 PC vs 管理后台

- **location:** FR-5「清空条件后，管理后台恢复全部关键词任务；剪辑手 PC 只恢复这名剪辑手已领取的任务」
- **trigger_condition:** 已领剪辑手在 PC 填条件查询后再清空；或未领剪辑手清空
- **why_unhandled:** 清空规则本身已写清；未写「当前查询结果统计」在空领取集 + 有筛选条件无命中时，统计是否按 0 还是沿用上次；也未写后台删除后清空是否应仍能扫到已删行
- **consequence:** 统计与列表基数不一致时，验收无法判断是筛选 bug 还是统计口径 bug（与 EC-5/EC-7 耦合）

### EC-9 「一任务一稿」与占用态「部分领取」并存

- **location:** §3 / FR-9「一个任务一个关键词一条稿件」「没有稿件包」；FR-5「占用是空闲、占用中、部分领取」
- **trigger_condition:** 帐号代发单条稿件进入占用状态机，出现或需要解释「部分领取」
- **why_unhandled:** 1.0 占用枚举被原样引入，但本增量否定稿件包与分次领取，未定义单稿场景下「部分领取」是否可达、是否禁止写入
- **consequence:** 实现者保留 1.0 状态迁移会在单稿上冒出「部分领取」；或擅自删掉枚举导致与「稿件相关状态与 1.0 一致」字面冲突

### EC-10 用户侧「一个用户 ID 一个平台关键词」与多稿领取尝试

- **location:** FR-7「一个用户 ID 一个关键词…不能再领另一个平台关键词的稿件」；FR-9/FR-10 一条稿消耗 1 次；UJ-4「这一条已经领走之后不能再领」
- **trigger_condition:** 用户已领走并下载平台关键词 A 的稿件后，再领同书关键词 B 或另一书平台关键词稿件；或未下载仅「领取成功」半态
- **why_unhandled:** 「领走并下载」与「领取成功」两套措辞并用（FR-7 / FR-12），未定义只领取未走完下载/保存相册时是否已占用那一个平台关键词名额
- **consequence:** 实现者若以下载完成才占用，用户可重复点领取占多次；若以领取成功即占用，下载失败会锁死唯一名额且无解法

### EC-11 收益按词切 vs 任务未上传 / 无用户领取

- **location:** FR-12 / §8；UJ-5 Edge「只有订单、没有用户领取，不切」
- **trigger_condition:** 关键词已产出已结算订单，但对应剪辑任务从未上传稿件，或稿件从未被用户领走下载
- **why_unhandled:** 「不切」已覆盖无用户领取；未写「有订单但无本链路稿件/无领取人」时官方收益是否仍入账、剪辑手字段是否空、是否允许人工补挂
- **consequence:** 账上官方有收益但永远切不出，或实现者把分成记给「最后上传者」等合同外角色

### EC-12 管理后台任务状态 vs 剪辑手 PC 任务状态两套枚举

- **location:** FR-2「任务状态是待发布、已发布、已领取未上传稿件、已上传稿件、已完成」；FR-5「任务状态只有未完成和已完成」「未上传之前，任务停在已领取」；FR-4 未写领取时状态迁移
- **trigger_condition:** 领取成功、上传成功、用户领完任一时刻，两端展示/落库状态需要对齐
- **why_unhandled:** 领取与上传时后台五态如何跃迁未写；PC「已领取」与后台「已领取未上传稿件」是否同一态未写；「已完成」在两端触发条件不同（PC=已回填 vs 后台完成含义未定义）
- **consequence:** 实现者各自映射，筛选「已领取未上传」与 PC「未完成」对不齐，批量下发/统计指标失真

### EC-13 审核状态非「未通过」亦非明确「通过」时下发

- **location:** FR-3「审核状态为未通过的词不能下发」；FR-2 列表含「审核状态」
- **trigger_condition:** 审核状态为空、审核中、或其它未枚举值时点下发
- **why_unhandled:** 只禁止未通过，未写必须通过才能下发，也未给审核状态完整枚举与默认值
- **consequence:** 实现者允许未审下发，或静默拦截；运营以为「已完成申词」即可发，实际卡在未写明的审核门闩

### EC-14 稿件已驳回 / 上传失败后能否再传

- **location:** FR-5「每个任务只能上传 1 个稿件，传完后不再显示上传稿件」；上传态「已上传、上传中、上传失败」；审核「已通过、审核中、已驳回」
- **trigger_condition:** 首次上传失败，或审核已驳回，剪辑手再次上传
- **why_unhandled:** 「只能 1 个」与失败/驳回是否占用那唯一名额未写；未写替换、撤回、驳回后重传
- **consequence:** 失败即永久锁死该词任务，或实现者允许覆盖后与「一条稿件」溯源/已领取用户下载内容不一致

### EC-15 批次内部分关键词已下发、部分仍待发布时的领取面

- **location:** FR-2 勾选「批量下发任务」；FR-3 单条下发；FR-4 卡片按书聚合「已下发、可供领取」数量
- **trigger_condition:** 同书同批申请中，运营只下发部分行，其余仍待发布；剪辑手此时领取该书
- **why_unhandled:** 与 EC-1 同源：领取只吃当前已下发集合已暗示，但未写书卡片在「部分待发布」时是否仍可领、领取后待发布行与已领书的关系、批量下发是否允许跨已领/未领书混选
- **consequence:** 部分下发被当成整书可领；或禁止部分下发却无合同依据——实现分叉后，EC-1 更易被做成静默数据窟窿

## Handled（静默丢弃，仅备查）

- 非剪辑手可见不可领（UJ-2 / FR-4）
- 自动执行中不可下发；非待发布不可再下发；未通过不可下发（FR-3）
- 授权项目外不可提交申词（FR-2）
- 清空查询：后台回全部、PC 回本人已领（FR-5 明文）
- 批量上传只匹配本人已领未传、已有稿跳过（FR-5 方向已写；拒绝细节见 EC-6）
- 无用户领取或无订单则不切分成（UJ-5 / FR-12）
- 比例之和 > 100 不可保存（FR-1）
- 次数不足不可领（FR-10）
- 帐号代发无稿件包、不选词（FR-7/FR-9）

---

## Verdict

合同在「一书一领」「PC 只见已领 / 后台见全部」「一任务一词一稿」「按词切分」主路径上有明确终态，但对**部分下发 + 事后补下发**、**并发领取**、**删除行语义**、**领取/下载半态占名额**、**两端任务状态映射**、**失败/驳回重传**、**占用态部分领取**等边界未闭合。实现者若自行猜测，最容易在「已领书无法承接新词」与「双端状态/统计不一致」上产生不可验收分叉。
